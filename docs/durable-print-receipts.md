# 永続的な印刷受付記録（opt-in）

`RAKUSIKA_PRINT_RECEIPTS_DIR`に永続ディスク上の専用ディレクトリを指定し、POST /printer/printへ16〜128文字の`Idempotency-Key`を付けると有効。同じ物理プリンターを扱うプロセスは同じ記録ディレクトリを使う。記録にはラベル内容のコピーを含めず、要求ハッシュとHTTP結果を保持する。ディレクトリ0700・ファイル0600。

排他的作成した受付記録と親ディレクトリをfsyncしてから既存印刷処理を一度だけ呼ぶ。結果はfsyncとatomic renameで保存する。同じID・内容の再送には保存した結果を返す。内容が異なる場合409。処理途中・破損・結果保存失敗はPRINT_OUTCOME_UNKNOWNで停止し、物理印刷を自動再実行しない。部分印刷エラーも記録して同じIDでは繰り返さない。明示的な再印刷は出力・キューを確認したうえで新しいIDを発行する。

再起動後も記録を保持する。TTLや自動削除はしない。応答がpendingの場合、再送結果は受付時のpendingであり、その後のCUPS状態は既存ジョブ照会APIで確認する。doneも利用者の目視確認を代替しない。

設定なしでID付き要求を受けた場合503で印刷前に停止。ヘッダーなしの既存LAN APIは従来どおり。既存LAN制限内で動作し、Bluetooth端末・施設・ユーザー認証を追加するPRではない。Lite側の要求ID永続化とUI連携、実機再起動試験は別途必要。

ロールバック時は記録ディレクトリを残す。旧バイナリはIdempotency-Keyを認識しないため、未確定要求を旧バイナリへ再送しない。クライアントの新経路を止めてジョブ状態・実物を確認してから旧バイナリへ戻す。実機では配備前のバイナリSHAと設定を固定し、復旧後health・計量接続・レンダリングを検証する。

自動検証: 再起動を模した新ハンドラー、同時送信、途中panic、部分失敗、新IDでの明示再実行、永続化設定なし、不正ID/JSON、破損記録、旧呼び出しをテスト。実機部分印刷は別証拠としてOfficeジョブ304、補充後の正常印刷は305を記録。

クライアントは送信前にGET /versionのfeaturesにdurable-print-receipts-v1があることを確認する。旧Hubは未知ヘッダーを無視するので、能力確認ができない場合は印刷しない。ディレクトリ未設定時は上記503となり、物理出力しない。

実機検証（2026-10-26、Office Pi 5、commit 0e38fd0）: TEST-03を1要求送信しジョブ306 done。同じID/内容の直後の再送とHub再起動後の再送で同じ応答を取得。Hubログの印刷呼び出しは1回。ユーザーの枚数確認は別途待機。試験後は元バイナリSHA 023b3f0423d1923c638d1b06167e4131883872ca8c1f07c9172eba20c84be7e0と元稼働版へ復旧。印刷healthは正常。計量器は試験版起動前から応答タイムアウトのため、計量復旧ゲートは未合格。後続差分はversion能力表示のみで、物理試験対象の印刷処理は同一。


## v2: 印刷を実行しない結果照会と旧版へのロールバック

`durable-print-receipts-v2` の機能表示は次の専用URLへの対応を示す。受付ディレクトリが未設定なら503で拒否するため、機能表示だけを設定完了の証拠にしない。

- `POST /printer/print/durable`: `Idempotency-Key`必須。既存のラベル生成・印刷処理へ同じ永続受付ラッパーで渡す。旧HubにこのURLはなく、受付番号を無視して印刷されることを防ぐ。
- `GET /printer/receipts/{requestId}`: 保存された受付だけを読む。印刷や再印刷を実行しない。記録済みなら200、`receiptState: recorded`、元のHTTPコード`httpStatus`、応答本文文字列`responseBody`を返す。
- 記録が見つからなければ404（その時点で未確認）。処理中・中断・壊れた記録は409/PRINT_OUTCOME_UNKNOWN。エラーや404を理由に新しい要求IDで自動再印刷しない。

`recorded`は印刷受付に関する応答を記録した意味であり、物理印刷完了ではない。元の`printState: pending`やCUPSジョブIDを維持し、プリンター・キューの確認に使用する。

この変更は既存LANモードの拡張。Bluetooth用の端末・ユーザー・施設認可が完成したことを意味しない。インターネットへ公開しない。受付ディレクトリは更新・ロールバック後も保持する。削除や再初期化をまたぐ重複防止は保証できない。

後続の実機確認: ユーザーがTEST-03は1枚と確認した。計量器の電源投入後、8ce7a9aを使用した旧版・新版・Hub再起動・旧版への復旧の各段階で0 kg/stableを確認し、元バイナリのSHAと版情報を復元した。上記の初回試験時点の「枚数確認待ち」「計量未合格」は、この後続確認で更新される。既知重量での計量精度やPi OS再起動試験まで済んだことは意味しない。
