# 体験速度改善 第1段階：画面を変えない印刷確認

2026-11-03。計測済みの main/dev を起点に、専用ワークツリー `raku-sika-hub-backend-20261103` / `feat/experience-backend-20261103` で実施。既存の計測・配備用ワークツリーは変更しない。

## 対象と変更しない契約

印刷の2秒周期のCUPS確認待ちを対象とする。ラベル生成、送信順序、プリンタのmutex、APIの型、画面、操作、文言、印刷再送の判断、rakuqlの機器確認は維持する。物理印刷を早める変更とは位置付けない。

正常時は250ms間隔で未完了ジョブ一覧のみ取得する。終了時だけプリンタ状態を取得し、確認中のデバイスURI取得をなくす。確認1回あたりの子プロセスは3から1になるが、単位時間の起動数は増える（旧：約1.5回/秒、新：最大約4回/秒＋終了時1回）。Pi上のCPU・CUPS負荷を未検証のまま本番効果を断定しない。

読取失敗は従来の2秒待機で再確認する。失敗が無出力だった場合も、空キューと扱わずエラーにする。待機時間は残り期限で切り詰め、期限時点で消えたジョブは成功側の既存確認経路へ渡す。外部コマンド実行時間はこの待機期限とは別であり、この変更でコマンドハングの上限を保証するものではない。

キューから消えたことと印刷機器の成功報告は別の段階のまま。rakuqlの失敗・未確認・用紙エラーを成功へ変換しない。既存の結果ファイル欠落時のフォールバックは変更対象外で、その挙動をテストに残す。

## 検証

- 仮想時計で0ms、境界直前/直後、3.160秒、4.869秒等の完了を再生。確認間隔による遅れが250ms未満で、他ジョブが残っても対象ジョブだけを判定する。
- 永続待機、期限時の完了、CUPS停止・復旧、無出力でのコマンド失敗を検証する。
- 実際のシェルスタブを使い、待機中は一覧だけ、返却時は状態だけを取得することを確認する。
- 既存のラスタ同一性、機器成功・未確認・失敗テストを継続する。
- `go vet ./...`、`go test -race ./...`、`VERSION=validation-experience scripts/build-release-arm64.sh /tmp/raku-sika-hub-experience-validation-20261103` をローカルの通過条件とする。

再生例では3.160秒の完了を3.250秒、4.869秒を5.000秒で検出する。外部コマンド時間や実機排出を含まない試験であり、本番の改善値ではない。

## 次の段階と撤回条件

ローカル検証の通過後に、別のLiteワークツリー/PRで「同じ個体・部位を続けて入力する」試験機能を扱う。従来動作を既定とし、利用者が提案から選んだ場合だけ変更する。戻せること、重量を持ち越さないこと、エラー時に次の登録へ進めないことを検証し、UIのPRには合成データのスクリーンショットを載せる。

実機配備は別の検証段階。開発機で負荷と応答を比較し、CUPS負荷増、応答悪化、順序の変化、誤成功があれば採用しない。本番への新たな配備や検証印刷は、このPR作成には含まない。旧版へ戻せる配備手順と、今回の確認変更だけを戻せる差分を維持する。
